# Quickstart: 将机器人唤醒词改为“小智，小智”

## 目的

这份文档用于验证本次需求在页面层、配置层和真实机器人语音链路上的表现，而不是用于描述具体实现代码。

## 前置条件

1. wire-pod 已能正常启动，机器人已完成接入
2. 当前环境可以访问 `chipper` 配置页和 SDK 页面
3. STT 服务为 `vosk` 或 `whisper.cpp`
4. 已安装或可下载 `zh-CN` 对应模型
5. 若要完成最终语音验证，需要真实机器人和可说话的现场环境
6. 如需验证 jdoc 回写，需要本地 `chipper/jdocs/jdocs.json` 可写

## 验证分层

为避免把“页面文案已切换”误判成“真实热词已替换”，本次验证必须分三层执行：

1. **页面 / 配置层**：确认 setup 页面、SDK 页面、接口返回值和提示文案已经切换
2. **机器人设置 / jdoc 层**：确认 `locale`、`button_wakeword` 等设置能从接口读取并回写到 `jdocs/jdocs.json`
3. **真实语音层**：确认对机器人说“小智，小智”后是否真的进入问答链路

只有第三层成功，才能把“真实语音热词已生效”判定为通过。

## 验证场景 1：中文 STT 前置条件

**目标**: 确认 `chipper` 已切到中文 STT 语言。

1. 打开 setup 页面中的 STT 语言设置
2. 选择 `Chinese (CN)` / `zh-CN`
3. 提交设置
4. 观察页面提示是否成功
5. 必要时读取 `/api/get_config`，确认 `STT.language` 为 `zh-CN`

**预期结果**:

- 页面提示语言切换成功，或开始下载中文模型
- `apiConfig.json` 中的 `STT.language` 最终为 `zh-CN`
- 若进入下载流程，页面必须明确显示“Downloading model...”或等价状态

## 验证场景 2：SDK 页面默认体验切换

**目标**: 确认用户可见默认唤醒文案已切到“小智，小智”。

1. 打开 SDK 设置页
2. 查看与 `Hey Vector` 相关的按钮、状态提示和当前设置文案
3. 刷新页面并再次确认

**预期结果**:

- 默认展示文案已切换为“小智，小智”
- 页面中不再把 `Hey Vector` 当作默认推荐入口展示
- 若旧接口入口因兼容性保留，页面文案必须把它表述为兼容能力，而不是默认入口

## 验证场景 3：机器人 locale 和设置回显

**目标**: 确认机器人设置链路仍然可用。

1. 在 SDK 设置页切换 locale
2. 调用 `/api-sdk/get_sdk_settings`
3. 检查返回的 jdoc 中是否包含最新 `locale`
4. 刷新页面确认当前值能正确回显
5. 检查 `chipper/jdocs/jdocs.json` 中 `vic.RobotSettings` 是否已更新

**预期结果**:

- SDK 设置接口可正常写入机器人设置
- `jdocs/jdocs.json` 可缓存新的 `vic.RobotSettings`
- 页面刷新后回显一致

## 当前环境实测结论

以下结论来自当前真实机器人环境的实际验证，不是设计推断：

| 检查项 | 结果 | 证据 / 备注 |
| --- | --- | --- |
| `/api-sdk/get_sdk_info` | 通过 | 返回机器人 `003097ff`，IP 为 `192.168.1.39` |
| `/api-sdk/get_sdk_settings?serial=003097ff` | 通过 | 返回 `locale = "zh-CN"` |
| `/api-sdk/trigger_wake_word?serial=003097ff` | 失败 | host 侧返回 `500`，原因是访问 `http://192.168.1.39:8889/consolevarset` 超时 |
| 机器人 `192.168.1.39:8889` | 不可达 | `curl` 超时，`nmap` 显示 `8889/tcp filtered` |
| 说“小智，小智” | 失败 | 机器人未进入聆听状态 |
| 说“hey, vector” | 失败 | 机器人未进入聆听状态 |
| 物理按钮唤醒 | 通过 | 机器人可进入聆听状态，并能正常回答问题 |

## 当前结论判定

基于以上实测结果，当前环境可得出以下判定：

1. `sdkapp` 与机器人设置链路是通的，`locale = zh-CN` 已成功写入并可读回
2. `/api-sdk/trigger_wake_word` 只是兼容接口，依赖机器人开放 `:8889/consolevarset`；当前机器人环境未开放该能力，因此不能把它作为主验证入口
3. 旧唤醒词和新唤醒词都无法让机器人进入聆听状态，说明当前阻塞点不在页面文案或 host 侧问答链路，而在机器人侧 spoken wakeword / hotword engine
4. 物理按钮唤醒后可以正常回答，说明 `wire-pod` 主问答链路仍然可用；本轮需求未能在真实环境中证明“说出小智，小智即可唤醒”
5. 因此，当前最准确的结论是：**仓库内的 UI、locale、配置和兼容说明已经落地，但真实语音热词替换仍受机器人固件或外部唤醒能力限制**

## 已知限制记录

如果出现以下情况，需要明确记录：

1. 页面和配置都已切换，但真实语音“小智，小智”仍不能唤醒
2. `vector-cloud` 仍将 `zh-CN` 回退到英文语言码
3. 机器人固件或上游热词检测不支持本次目标短语

这些情况都应视为“外部能力限制或链路风险”，而不是简单归类为页面实现失败。

## 当前仓库级限制

1. 当前 `vector-cloud/internal/voice/process.go` 会接收 `zh-CN` locale，但底层 `chipperpb.LanguageCode` 依赖只提供 `ENGLISH_US`、`ENGLISH_UK`、`ENGLISH_AU`、`GERMAN`、`FRENCH`
2. 因此，当前仓库无法把 `zh-CN` 真正映射到一个中文 `LanguageCode`，只能显式记录为英文回退
3. 这意味着页面、jdoc 和 locale 可以切到中文语义，但“真实热词后续链路是否完全中文化”仍然受上游协议与固件能力限制
